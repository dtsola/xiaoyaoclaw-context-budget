- **指令来源**：用户 2026-09-14 11:05 —— 「默认上下文大小定死 200k，实际按厂商模型不同，导致提前压缩/卡顿/长任务跑不完；应产出 skill 自动优化，阈值 = 厂商标称窗口的 60%，用量 80% 时自动压缩」

---

## 0 一句话结论

**200k 不是"写死"，它是 OpenClaw 的兜底默认值**（源码 `DEFAULT_CONTEXT_TOKENS = 2e5`）；真正缺的是**比例语义**（60% 上限 / 80% 触发）和**按模型取值**——现在这两件事都得人工把比例换算成绝对 token 数写进配置。

做法：把换算自动化 + 一条命令落配置 → 产出技能 `context-window-budget`。

---

## 1 事实基础（全部取自本机）

### 1.1 窗口解析链（源码 `src/agents/context.ts` → `resolveContextWindowInfo`）

1. `models.providers.<provider>.models[].contextWindow`（配置覆写，**最高优先**）
2. 模型注册表里的 `contextWindow`
3. 兜底 `DEFAULT_CONTEXT_TOKENS = 200000` ← **你说的「定死的 200k」就是这一条**
4. 之后若 `agents.defaults.contextTokens` 更小，则用它下压

### 1.2 本机现状（`openclaw.json` + `/status` 实测）

| 项 | 现值 | 说明 |
|---|---|---|
| deepseek-flash / deepseek-v4-pro | `contextWindow: 500000` | 配置里被人工覆写；`/status` 实测 `Context: 62k/500k (12%)` → **本机已绕过 200k** |
| minimax 全系 | `contextWindow: 200000` | 与厂商标称重合，凑巧 |
| `agents.defaults.contextTokens` | **未设** | 无全局天花板 |
| `compaction.reserveTokens` | **未设** | 走 Pi 默认 16384 → 被 `reserveTokensFloor` 抬到 **20000** |
| `compaction.reserveTokensFloor` | **未设** | 默认 20000 |

→ **当前实际触发点 = 500k − 20k = 480k（窗口的 96%）**：几乎等于没有注意力保护；同时一旦某模型没进配置覆写，立刻掉回 200k 兜底、触发在 180k（提前压缩）。

### 1.3 压缩触发公式（Pi 语义，OpenClaw 不决定）

```
触发条件：contextTokens > 有效窗口 − reserveTokens
reserveTokens = max(配置的 reserveTokens 或 Pi 默认 16384, reserveTokensFloor)
```

### 1.4 能力边界（schema 实证 —— 决定了方案形态）

- ✅ 每模型可配：`models.providers.*.models[].contextWindow`
- ✅ 全局可配：`agents.defaults.contextTokens`、`agents.defaults.compaction.*`
- ❌ **不存在**：`agents.list[].contextTokens`、`agents.list[].compaction`（无法逐 agent 覆盖）
- ❌ **不存在**：任何"按比例"的压缩阈值字段

→ 结论：**60% / 80% 必须换算成绝对 token 落配置**；且 `reserveTokens` 全局唯一（异构窗口时的硬约束，见 §3-A2）。

## 2 换算公式（把你的最佳实践固化成算术）

设厂商标称窗口 `W`：

```
cap（有效窗口）      = floor(0.6 × W)      → 写进该模型 contextWindow
reserve（预留）      = floor(0.2 × cap) = floor(0.12 × W)
触发点               = cap − reserve = 0.8 × cap   ✅ 即你要的「80% 用量自动压缩」
兜底自检（关键）     = reserveTokensFloor 必须 ≥ reserve − 4000
```

**为什么最后一条是坑**：memoryFlush（压缩前记忆落盘）的阈值用的是 `reserveTokensFloor` + `softThresholdTokens(4000)`，而压缩阈值用的是 `reserveTokens`。若只改 reserve 不改 floor，会出现：

```
本机若只设 cap=300k / reserve=60k（floor 仍 20000）：
  记忆落盘阈值 = 300000 − 20000 − 4000 = 276000
  压缩阈值     = 300000 − 60000       = 240000
→ 压缩先触发，记忆落盘永远不会跑（压缩前不落盘 = 上下文被直接吞掉）
```

### 本机算例

| 模型 | 厂商标称 W | cap（60%） | reserve（12%W） | 触发点 | 触发点/厂商窗口 |
|---|---|---|---|---|---|
| deepseek-flash | 500,000 | **300,000** | **60,000** | 240,000 | 48% |
| minimax 全系 | 200,000 | 120,000 | 24,000 | 96,000 | 48% |

> ⚠️ 两个 reserve 值冲突（60k vs 24k），因为全局只能有一个 —— 见 §3-A2 取舍。

## 3 方案 A：配置层直接落（零代码，今天可用）

### A1 单模型族（= 本机现状：7 个 agent 全跑 deepseek-flash）

patch 预览（**未执行，等你批**）：

```json5
{
  agents: { defaults: { compaction: {
    reserveTokens: 60000,        // = 0.2 × cap
    reserveTokensFloor: 60000,   // 必须同步，否则 memoryFlush 失效
  } } },
  models: { providers: { deepseek: {
    models: [
      { id: "deepseek-flash",  contextWindow: 300000 },   // 0.6 × 500k
      { id: "deepseek-v4-pro", contextWindow: 300000 }
    ]
  } } }
}
```

- **不建议**用 `agents.defaults.contextTokens` 落 60%：它是「全模型天花板」，将来接入 1M 窗口模型会被它隐性压死。要设就设 400k 级"保险丝"，而不是 300k 业务值。
- `reserveTokensFloor` 与 `reserveTokens` 同时设 60000，是为了让记忆落盘（236k）真实发生在压缩（240k）之前。

### A2 异构窗口（将来 minimax / 其他供应商混用）

reserve 全局唯一 → 三种取舍：

| 取舍 | 做法 | 后果 |
|---|---|---|
| ① **取主力模型的 reserve（推荐）** | reserve = 60k | 主力（deepseek）精确命中 80%；小窗口模型会**提前**压缩（偏保守，安全） |
| ② 取最小 cap 的 reserve | reserve = 24k | 小窗口模型精确；主力模型 92% 才压缩 = **等于放弃注意力保护** |
| ③ 切换即重算 | 切模型时跑 `set-model` 脚本改 reserve（技能提供），重启 ~10s 生效 | 唯一能同时精确的路子，代价是切模型有动作 |

### 代价与验收

- **代价**：压缩会更频繁（每次压缩 = 一次额外 LLM 调用 = 你说的卡顿来源之一）+ 历史有损（但 `keepRecentTokens: 20000` / `maxHistoryShare: 0.3` 已在位，兜住连续性）
- **验收**：`/status` 看 `Context: x/300k`、`🧹 Compactions` 计数变化、长任务不再中断
- **附带风险**：reserve 60k 远超本机 `maxTokens: 8192` 的机械需要 —— **这 60k 是为「注意力」买的，不是为「溢出」买的**，别指望它省 token；cap 变小后 bootstrap 注入（`bootstrapTotalMaxChars` 150k 字符）占比会上升，建议同步收敛

## 4 方案 B：技能化（`context-window-budget`）

> 用户原话：「可以产出一个 skill 来自动进行优化」

### 目录结构

```
context-window-budget/
├── SKILL.md                  # 何时用、公式、铁律（含"为什么是 60/80"）
├── vendors.json              # 厂商标称窗口唯一真源：provider / model / window / source_url / collected_at
└── scripts/
    ├── plan_context_budget.(py|ps1)   # 只读：算 cap/reserve/floor + 冲突报告 + patch 预览
    ├── apply_context_budget.*         # 落配置（必须 --yes，走 gateway config.patch）
    ├── verify_context_budget.*        # 重启后校验实际生效值
    └── switch_model_budget.*          # 切模型时重算 reserve（解决 §3-A2）
```

### 命令行为

| 命令 | 行为 |
|---|---|
| `plan` | 读 `vendors.json` + 本机 `openclaw.json` + 当前激活模型 → 输出每模型 cap/reserve/floor、**冲突报告**（异构时给三选一建议）、patch 预览。**默认只读** |
| `apply --yes` | 走 gateway **`config.patch`（永不 `config.apply`**，符合配置铁律）+ 写审计日志 + 提示重启 |
| `verify` | 重启后读 `session_status` / `openclaw sessions`，校验 `Context: x/cap` 与 reserve 一致；不一致报警 |
| `set-model <model>` | 切换模型时重算 reserve 并落配置 |
| `audit`（可挂 cron 每周） | 发现三类漂移：新模型落回 200k 兜底 / floor-reserve 顺序倒置 / 比例偏离 |

### 设计要点

- **参数化**：`--cap-ratio 0.6`（默认）、`--compact-at 0.8`（默认）→ 你的最佳实践写进默认值，但可覆盖
- **防呆**：cap ≥ 16k（源码 hard min，低于会被 block）；< 32k 警告；比例限 0.1–0.9；改动前备份；不落明文密钥；审计日志进 `memory/`
- **溯源**：`vendors.json` 必须带来源 URL + 采集日期 —— 本机那个 `500000` 目前**无从溯源**，这正是技能要堵的第一个口子
- **沉淀**：SKILL.md 写清"60/80 是注意力保护，不是机械 headroom"，防止后人以为可随意放宽

## 5 当前能力边界（落不了的部分）

1. **没有 per-model 压缩阈值** —— Pi 只认一个 `reserveTokens`。真·「每模型 80%」需要上游加 `compactAtRatio` 或 per-model reserve。
2. **没有 per-agent 覆盖** —— 想让「长任务 agent」用 80% cap、「速答 agent」用 40% cap，现在做不到（只能靠切模型）。
3. **可选插件路线（P3，不建议先做）** —— `setCompactionSafeguardRuntime` / pruning runtime 是按 run 注入的，理论上写 runtime-plugin 可在每轮按模型动态设定窗口与 reserve；但属改运行时代码，风险与维护成本高 → **先 A 后 B，插件留作 P3**。
4. **建议向上游提 3 条 issue**：per-model `contextWindowRatio`；per-agent compaction 覆盖；按比例 reserve（`compactAtRatio`）。

---

## 6 顺带纠两个因（别只治阈值）

- **卡顿**：压缩本身是**同步**的大 LLM 调用，触发越频繁越卡。60/80 让频繁变得"可控"，但不会消除卡顿；真正要压的是**单次压缩体积**（`keepRecentTokens` / `maxHistoryShare` 已在位）。
- **长任务失败**：主因是 **overflow recovery**（超窗报错 → 回退压缩 → 任务上下文断裂）。60% cap 能让它基本不发生 —— **这是本方案最硬的收益**。
- **另两个吃窗口的大户**：① bootstrap 注入（上限 150k 字符）② 单条工具结果（上限 = 窗口的 30%，源码 `MAX_TOOL_RESULT_CONTEXT_SHARE = 0.3`）。小窗口模型上这两项会失控，建议与 cap 联动设阈值。
